## 边界与分层判定（Boundary Check）

> 每个含设计阶段的变更（Full / legacy Hotfix）必须先回答本节，答案须与项目现行《边界契约》一致；项目无契约时按通用规则填写并标注「无项目契约」。
> 纯配置类 tweak、direct Hotfix、无 design 工件的 Quick 变更免填本节。

- **归属层**：本变更属于哪一层（平台内核层 / 行业包层 / 客户定制层；单仓库项目可写通用模块层 / 业务模块层 / 配置层）。
- **判定理由**：为什么属于该层而不属于相邻层（对应契约三问：全行业/全产品通用？→内核层；同行业共享？→行业包层；单客户特化？→定制层）。
- **仓库与模块落点**：实际改动的仓库、模块、包路径；是否跨仓库、跨模块、跨前后端。
- **扩展方式与优先级自查**：按「配置 > 低代码/配置化 > 扩展点(SPI) > 新增模块 > 改内核/通用层」的优先级，本变更采用哪一级？为什么上一级解决不了？
- **禁止项自查**：是否存在以下任一情况（无则写「无」；有则必须先回退 specifying 重定方案，不得进入 DP-2）：
  - 直依赖内核/通用层的 Impl 实现类（只准依赖 api 接口或实现 SPI）
  - 为单个客户/单个行业的差异直接修改内核或通用层逻辑
  - 跨模块直注他模块 Mapper/实体（应走他模块暴露的只读 Api）
  - 绕过公开接口直接写共享/内核数据表
  - 在通用层放入带行业/客户语义的业务实体
- **契约引用**：项目边界契约的路径与适用条款（vault 或仓库内相对路径）；本变更涉及 L1 改动时，附「对下游的影响面」。
